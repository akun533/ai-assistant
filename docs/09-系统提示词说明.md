# 09-系统提示词说明

## 1. 系统提示词的作用与价值

系统提示词（System Prompt）是人工智能助手在执行任务时遵循的指导性文档，它定义了 AI 的角色定位、行为准则、工作流程和技术规范。在本项目中，系统提示词扮演着至关重要的角色：

**核心价值体现在以下方面：**

1. **角色定义**：明确 AI 作为表单开发专家的身份定位，确保输出的专业性和一致性
2. **质量保障**：通过严格的检查规则和验证流程，确保生成的表单规则准确无误
3. **标准化输出**：统一不同 UI 框架的表单配置格式，降低使用者的学习成本
4. **流程控制**：预定义工作流程序列，引导 AI 按正确顺序执行任务
5. **错误预防**：通过核心原则和约束条件，避免常见错误和不当操作

## 2. 项目中的提示词文件列表和用途

本项目中所有提示词文件位于 `/ai-assistant/src/components/*/prompts/` 目录下：

| 文件路径 | 所属组件 | 用途说明 |
|---------|---------|---------|
| `common/prompts/common-prompt.md` | 通用组件 | 定义所有表单生成任务的通用基础规则 |
| `ta404-ui/prompts/ta404-ui-prompt.md` | ta404-ui | 银海 ta404-ui 表单框架的专用提示词 |
| `ta404-ui/tools/form/yinhai-features/control/control-prompt.md` | ta404-ui | 表单组件显示/隐藏、启用/禁用等条件控制配置 |
| `ta404-ui/tools/form/yinhai-features/event/event-prompt.md` | ta404-ui | 组件事件函数和全局工具函数的定义 |

**文件组织结构：**

```
prompts/
├── common-prompt.md          # 通用基础提示词（被所有组件引用）
├── ta404-ui-prompt.md        # ta404-ui 专用提示词（继承并扩展通用规则）
├── control-prompt.md         # 条件控制功能提示词
└── event-prompt.md           # 事件处理功能提示词
```

## 3. 提示词文件结构详解

### 3.1 common-prompt.md 结构

`common-prompt.md` 是整个提示词体系的基础文件，包含以下核心章节：

```markdown
## 核心原则 (core_principle)
- 定义 AI 的基本行为准则
- 包含：优先级规则、质量标准、更新策略等

## 沟通风格 (communication_style)
- 定义与用户交互的语言规范
- 强调自然、友好、简洁的对话方式

## 执行顺序 (execution_order)
- 工具调用的严格顺序要求
- 禁止跳过步骤或乱序执行

## 工具调用前沟通 (pre_tool_communication)
- 执行关键步骤时的自然语言说明
- 模拟对话感的语气指导

## 工作流序列 (workflow_sequences)
- 表单创建序列 (form_creation_sequence)
- 表单修改序列 (form_modification_sequence)
- 停止序列 (stop_sequence)
- 技术帮助序列 (code_sequence)

## 组件类型定义 (component_type)
- TypeScript 类型定义
- 表单组件的结构规范

## 检查规则 (check_rule)
- 组件配置的验证标准
- 必填属性和约束条件

## 标准流程指导 (operationType)
- 根据用户意图匹配对应的执行流程
- create/modify/code/other 四种类型

## 表单规则模板示例
- 完整的 JSON 格式参考示例

## 参考示例
- 不同 UI 框架的实际生成案例
```

### 3.2 ta404-ui-prompt.md 结构

`ta404-ui-prompt.md` 在继承 common-prompt 的基础上进行了银海框架的定制：

**主要差异和扩展：**

```markdown
## 核心原则 (新增/修改)
- 强调表单容器组件必须是根节点
- type 必须为 'form-container'，且存在且唯一

## 组件类型定义 (ta404-ui 专用)
```typescript
type ComponentRule = {
    type: string;              // 组件类型（必需）
    label: string;             // 标签
    fieldDecoratorId: string;  // 字段ID（必需）
    renderId: string;          // 渲染ID（必需）
    staticData?: object[];     // 静态数据（选择组件必需）
    dataType?: string;         // 数据类型，默认 static
    // ... 其他属性
};
```

## 检查规则 (ta404-ui 定制)
- 必填属性：type、fieldDecoratorId、label、renderId
- 选择组件需 3-8 个 staticData 选项
- 容器组件必须包含子组件

## 表单规则模板 (ta404-ui 格式)
- form-container 作为顶层容器
- formConfig 配置表单整体属性
- formColumns 定义表单列和子组件
```

## 4. 核心原则（core_principle）

核心原则是提示词中最重要的指导性规则，所有 AI 行为都必须遵守：

### 4.1 通用核心原则

```xml
<core_principle>
- workflow_sequences 拥有最高优先级，一旦匹配，必须立刻高效执行，禁止进入其他序列
- 获取工具结果后 → 先反思质量 → 再决定下一步
- 更新时仅改动必要部分，其余保持不变
- 表单既美观又实用
- 不要依赖历史记忆，重新调用工具确保信息准确性
- 确保只使用可用的组件，而非基于假设
- 确保所有组件都已正确配置和验证
</core_principle>
```

### 4.2 ta404-ui 专用核心原则

```xml
<core_principle>
- workflow_sequences 拥有最高优先级
- 执行表单创建/修改时，表单容器组件必须是整个规则对象的根节点
- type 必须为 'form-container'，存在且唯一（强制）
- 其他原则与通用规则一致
</core_principle>
```

### 4.3 核心原则解读

| 原则 | 说明 |
|-----|------|
| 优先级最高 | workflow_sequences 一旦匹配，立即执行，不进入其他序列 |
| 反思机制 | 获取工具结果后先评估质量，再决定下一步操作 |
| 最小修改 | 更新时只改动必要部分，保持其他内容不变 |
| 独立验证 | 不依赖历史记忆，每次重新调用工具获取最新信息 |

## 5. 工作流程序列（workflow_sequences）

工作流程序列定义了不同任务类型的标准化执行流程：

### 5.1 表单创建序列 (form_creation_sequence)

```xml
<form_creation_sequence>
1. **需求分析**
   - 理解用户需求
   - 制定完整操作计划并回复用户（强制）
   
2. **获取组件详情**（并行执行）
   - get_components_detail：查看所需组件的示例和配置（仅一次）
   - get_feature_template：如需功能特性

3. **规则生成**（原子操作）
   - 根据操作计划和组件示例一次性生成完整规则
   - 所有必需属性显式配置

4. **自检 & 修复**（强制）
   - 通过组件示例核对所有配置项位置
   - 审查规则是否符合 check_rule 要求
   - 问题自动修复后重新自检，无法修复则回退到规则生成

5. **复查**（强制）
   - 调用 validate_form_rule 函数进行复查

6. **推送规则**（强制）
   - 调用 push_current_rule 函数进行推送
   - 失败两次则结束流程
</form_creation_sequence>
```

### 5.2 表单修改序列 (form_modification_sequence)

```xml
<form_modification_sequence>
1. **需求分析**（并行执行）
   - 理解用户修改需求
   - 制定操作计划并回复用户（强制）

2. **必要信息**（并行执行，按需）
   - get_components_detail：获取使用和被修改的组件示例
   - get_feature_template：如需功能特性

3. **精确修改**（原子操作）
   - 基于 current_user_rule 调整规则
   - 保持其他部分不变

4. **检查**（强制）
   - 核对新增组件的配置项位置
   - 审查规则是否符合 check_rule 要求
   - 核对是否满足操作计划要求
   - 未通过则回退到精确修改

5. **复查**（强制）
   - 调用 validate_form_rule 函数进行复查

6. **推送规则**（强制）
   - 调用 push_current_rule 函数进行推送
</form_modification_sequence>
```

### 5.3 停止序列 (stop_sequence)

用于处理无效或不当的提问：

```xml
<stop_sequence>
1. 立即停止其他所有序列
2. 禁止输出相关内容
3. 只允许输出引导性问题，帮助用户明确具体需求
</stop_sequence>
```

适用场景：
- 与表单生成无关的问题
- 配置文件、敏感信息相关提问
- 工作流程或技术原理相关询问

### 5.4 技术帮助序列 (code_sequence)

```xml<code_sequence>
1. **问题分析**（并行执行）
   - 深入理解用户的技术问题
   - get_component_specs：如涉及表单组件

2. **提供帮助**
   - 判断问题类型：函数编写、技术咨询、代码调试等
   - 识别相关技术栈
   - 提供针对性的帮助内容
</code_sequence>
```

## 6. 组件类型定义（component_type）

### 6.1 通用组件类型定义

```typescript
type ComponentRule = {
    type: string;              // 组件类型（必需）,使用驼峰法
    title?: string;            // 标签
    field?: string;            // 字段ID
    name?: string;             // 组件名称
    _fc_id?: string;           // FormCreate 内部ID
    props?: object;            // 组件属性
    style?: object;            // CSS样式
    hidden?: boolean;          // 初始可见性
    $required?: boolean;       // 必填字段
    children?: ComponentRule[] | string[];  // 子组件
    col?: { span: number };    // 宽度（1-24，24=100%）
    validate?: ValidateRule[]; // 验证规则
    _fc_drag_tag?: string;     // 组件业务类型
    computed?: Computed;       // 动态计算规则
    $behavior?: Behavior;      // 组件事件处理
    on?: Event;                // 组件事件监听
    hook?: Hook;               // 生命周期事件监听
    effect: {
        fetch: FetchConfig;    // 加载远程数据
    },
    [key: string]: any;        // 允许其他属性
};
```

### 6.2 ta404-ui 组件类型定义

```typescript
type ComponentRule = {
    type: string;              // 组件类型（必需）
    label: string;             // 标签
    fieldDecoratorId: string;  // 字段ID（必需）
    renderId: string;          // 渲染ID（必需）
    style?: object;            // CSS样式
    required?: boolean;        // 必填字段
    placeholder?: string;      // 占位提示
    children?: {
        column: ComponentRule[]   // 放置子组件
    };
    dataType?: string;         // 填充数据类型，默认 static
    staticData?: object[];     // 静态数据，选择组件必需
    span?: number;             // 宽度（1-24，24=100%）
    [key: string]: any;        // 允许其他属性
};
```

### 6.3 FetchConfig 类型定义（远程数据加载）

```typescript
type FetchConfig = {
    action: string;              // 请求地址
    method?: 'GET' | 'POST';     // 请求方式
    to: string;                  // 响应数据插入位置
    query?: Object;              // GET 参数
    data?: object;               // 发送的数据
    dataType?: 'json' | 'formData'; // 数据类型
    headers?: Object;            // 请求头
    beforeFetch?: (config) => void | Promise | boolean; // 前置处理
    parse?: (res, rule, api) => any;                  // 数据格式化
    onSuccess: (body, rule, api) => void;             // 成功回调
    onError?: (e) => void;                            // 失败回调
}
```

## 7. 与 OpenClaw Skill 的对比

系统提示词和 OpenClaw Skill 都是项目中的重要组成部分，但它们服务于不同的目的：

| 对比维度 | 系统提示词 | OpenClaw Skill |
|---------|-----------|---------------|
| **定位** | 定义 AI 助手的角色和行为规范 | 定义具体技能/工具的能力 |
| **作用层面** | 战略层：指导整体任务执行 | 操作层：提供具体工具能力 |
| **内容** | 角色定义、工作流程、约束规则 | 工具函数、API 调用、参数规范 |
| **修改频率** | 相对稳定，频繁改动会影响一致性 | 根据功能需求经常更新 |
| **组织方式** | 嵌套式结构，支持继承和覆盖 | 独立文件，通过注册机制集成 |
| **示例** | common-prompt.md、ta404-ui-prompt.md | get_components_detail、push_current_rule |

### 7.1 协同工作方式

```
用户请求 → 识别 operationType → 匹配对应 workflow_sequence 
→ 按流程执行 → 调用 Skill 提供的工具函数 → 生成表单规则
```

1. **提示词** 决定"做什么"和"怎么做"
2. **Skill** 提供"用什么做"的具体能力

### 7.2 关键区别示例

| 场景 | 系统提示词规定 | Skill 提供 |
|-----|--------------|-----------|
| 表单创建 | 必须遵循 form_creation_sequence 流程 | get_components_detail 获取组件信息 |
| 规则验证 | 定义 check_rule 检查标准 | validate_form_rule 执行验证 |
| 规则推送 | 定义推送时机和失败处理 | push_current_rule 执行推送 |

## 8. 如何添加新的 UI 框架提示词

当需要支持新的 UI 框架（如 Element Plus、Ant Design Vue 等）时，按以下步骤添加：

### 8.1 创建提示词文件

**步骤 1：创建目录结构**

```bash
# 假设新框架名为 element-plus
mkdir -p /ai-assistant/src/components/element-plus/prompts
```

**步骤 2：创建框架专用提示词文件**

创建 `element-plus-prompt.md`，继承通用规则：

```markdown
# Element Plus 表单提示词

> 基于 common-prompt.md 的扩展规则

## 核心原则 (新增/修改)
<core_principle>
- 继承所有通用核心原则
- 新增框架特定约束（如有）
</core_principle>

## 组件类型定义 (element-plus 专用)
<component_type>
```typescript
type ElementPlusComponentRule = {
    type: string;              // 组件类型（必需）
    label?: string;            // 标签（部分组件可能不需要）
    field?: string;            // 字段ID
    // ... 其他框架特定属性
};
```
</component_type>

## 检查规则 (element-plus 定制)
<check_rule>
- 必须包含 type
- 表单组件必须包含 field 和 label
- 继承通用检查规则
</check_rule>

## 参考示例
### 创建新表单
...
```

### 8.2 关键配置项调整

根据新框架的特性，调整以下配置：

**1. 组件类型定义**

```typescript
// 通用定义
type ComponentRule = {
    type: string;
    field?: string;
    title?: string;
};

// 新框架可能需要调整字段名
type NewFrameworkRule = {
    type: string;
    fieldDecoratorId: string;  // 或其他字段名
    label: string;             // 或其他字段名
};
```

**2. 检查规则**

```xml
<check_rule>
- 必须包含 type
- 根据框架规范调整必填字段
- 选择组件的选项数量范围
- 容器组件的嵌套规则
</check_rule>
```

**3. 工作流序列**

通常不需要修改工作流序列，但可能需要调整工具函数调用。

### 8.3 注册新框架

**步骤 1：创建对应的组件模块**

```
src/components/element-plus/
├── prompts/
│   └── element-plus-prompt.md
├── tools/
│   └── form/
│       └── ... (如需功能扩展)
└── index.ts
```

**步骤 2：在项目中注册**

根据项目架构，在组件注册或配置文件中添加新框架的引用。

### 8.4 注意事项

1. **保持结构一致**：新提示词文件应保持与现有文件相似的章节结构
2. **继承通用规则**：优先继承 common-prompt.md 中的规则，避免重复定义
3. **明确差异点**：清晰标注与通用规则的差异部分
4. **提供示例**：添加该框架的实际使用示例
5. **文档同步**：更新相关文档说明新增的框架支持

### 8.5 检查清单

添加新框架提示词后，检查以下项目：

- [ ] 文件位置正确，位于 `prompts/` 目录下
- [ ] 核心原则包含或继承了通用原则
- [ ] 组件类型定义与框架规范一致
- [ ] 检查规则已适配新框架
- [ ] 至少提供一个完整的参考示例
- [ ] 文档已更新，说明新增的框架支持
